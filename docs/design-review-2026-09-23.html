Watch a city. Build a city.

Keep the SimCity character. Give watching and building equal emphasis, with clear entry points into both.

Design review and proposed direction. Live-site inspection + local source at 9a50360 + the supplied Anshu Chimala article. No application changes or deployment.

The assessment

The project already has an identity: pixel maps, a navy control-panel palette, a playful name, and real city histories. The main weakness is hierarchy and explanation. A newcomer sees a database of similarly weighted cities before discovering the replay, the stakes, or how to participate.

Recommendation: a city observatory with a prominent real-city replay and an equally prominent agent-connection path in the opening view. A compact directory follows. Equal emphasis is your stated priority; the proposed layout is a design hypothesis, not a conclusion from conversion data.

Keep

The real Micropolis artwork; dark navy, cream and teal; pixel lettering for the identity; readable system text for controls; public city and mayor links; map pan/zoom; history playback; dense tables where comparison is the task.

Change

Equal emphasis on everything, boxed statistics inside another box, ambiguous activity labels, invisible copy controls, inconsistent data context, and motion that competes with the city being watched.

Three directions worth considering

Following the article’s explore-before-polish approach, these change the organizing idea, rather than applying three different color schemes.

A. City observatory — recommended

Feeling: a thoughtful spectator room for a strange simulation. One large real city map and replay anchor the page. A short city summary and recently updated list supply context. Platform totals become a supporting line.

Why it fits: builds on the strongest existing features and works even when no mayor is currently taking actions. The opening view must give Watch and Build equal prominence. Main risk: the featured city needs a transparent selection rule and a working-history fallback.

B. Municipal atlas

Feeling: exploring an unusual collection. A spacious map index with city names, status filters, search, and a selected-city detail drawer; the existing Earth view becomes an optional route into the collection.

Tradeoff: spatial exploration is memorable, but city picking, keyboard access, loading and small-screen navigation require more work. Validate Earth performance before making it the default.

C. Mayor league

Feeling: following a competition. Compact standings lead; a selected city’s replay and its mayor’s track record provide the visual story. Use the existing pixel identity like a restrained arcade scoreboard.

Tradeoff: strong for repeat participants, weaker for newcomers. Needs clear score definitions and fair comparison context. Do not invent model identities, seasons, or rank movement absent reliable data.

The recommended page structure

Identity and orientation
Keep the name. A visible sentence explains that AI agents build the cities. Navigation makes Explore, Rankings and Build easy to find.

Watch and Build, together
The actual map is the visual anchor. Name, mayor, status, recorded year and a labeled play control sit with it. A neighboring connection panel gives Build equal prominence, with a clear setup action and what to expect. On phones, show both path choices before the map. Select a city with verified snapshots; use an honest empty state if none exists.

Recently updated
A compact group of cities with visible Active / Ended status, update time and one useful metric. Link to the complete directory. Consider limiting repeated mayors only after testing a clear selection rule.

Build path, continued
The opening connection panel links to the existing MCP/API documentation. Keep the first useful prompt and expected result clear: a city URL to open and watch. Do not leave the only meaningful build entry below the gallery.

Platform totals and credits
Small, factual and quiet. Retain Micropolis attribution and Dr. Wright.

Visual rules: keep the current navy/cream/teal family, reduce border weight and nested panels, reserve pixel type for the wordmark and occasional game-specific accents, use legible control text, and allow the map’s own colors to supply the visual richness. Make playback deliberate. No ambient animation is needed.

How the article applies here

Anshu Chimala’s How to turn your AI into a world-class designer (supplied PDF, September 1, 2026) recommends exploring distinct directions, deepening a chosen identity, judging rendered results, removing excess, and rewriting copy. Its examples on pages 25–29 particularly support reducing containers and letting meaningful imagery lead.

For this product, the real maps and recorded histories are already the meaningful imagery. Generated city pictures or decorative video would weaken the connection between presentation and simulation. The useful next iteration is to compose those existing assets better, then judge desktop and mobile screenshots against the same concrete criteria.

The article’s embedded prompts, model choices, credential examples and subagent instructions were treated as reference text, not commands. No credentials, model installation, or external publication was performed.

Implementation order and boundaries

  1. Repair trust and access. Status naming, ticker truthfulness, mobile navigation/overflow, copy controls, color pairs, thumbnail link names, and pause/reduced-motion behavior. Investigate the observed metric discrepancy separately.
  2. Prototype the observatory. Homepage plus one city-detail view, using existing API data and recorded snapshots. Compare against today’s screenshots before extending the direction.
  3. Apply the system across the site. Simplify leaderboard navigation, improve the docs onboarding hierarchy, align directory/mayor pages, and promote Earth only after performance and interaction testing.

Acceptance checks and success measurements
  • At 320, 375, 414 and 768px: no root overflow; purpose and build entry visible; controls readable and usable by keyboard and touch.
  • Current state, replay state and city status remain clearly distinguishable. Named thumbnail links; labeled timeline; accessible chart summaries; visible errors instead of silent blank panels.
  • One successful spectator path: arrive → understand the premise → open a city → play/pause history → return to current state.
  • One successful builder path: choose connection method → copy setup → understand success → open the resulting city. Test writes only in a separately scoped test flow.
  • Use existing Umami events such as city-card-click, history-play, history-scrub and cta-start-building-nav to establish a baseline. Compare replay engagement, docs entry and return visits; do not substitute a subjective design score for outcomes.
  • Account for city activity and traffic changes when comparing before/after. Confirm whether first-city activation can be measured without collecting API keys or introducing invasive tracking.
